# 验证技能的驱动选择

目标是维护可重复执行的 verification skill 和用户功能地图，不修改 MessageHub 的产品行为。本目录是唯一维护源，不复制另一份全局 profile 技能，不接生产，不提交或推送。

## 现状与选择

现有资产包括 `scripts/go`、真实 Store/HTTP/MCP 测试、真实二进制 smoke，以及一次交付报告。没有项目专用验证技能或 feature map。

方案 A 只包装已有 go test。优点是代码少、能复用 TTL/并发负例；但部分测试直接写 Store/SQL，部分业务后端是 fake。真实二进制 smoke 没有完整 MCP 文件入口，备份也没有启动第三个真实服务实例。因此 A 仅作为补充层，不能成为用户入口的全图证明。

采用方案 B。在技能自身目录内构建一个黑盒驱动，复用既有隔离入口和已锁定的官方 MCP SDK。主 agent 运行驱动，真实 CLI 配置和审批、真实 HTTP/SDK 调用、真实子进程恢复都在同一受控运行中完成。不重写 MCP/SSE 协议，不增加包或产品测试端点。

## 数据与状态归属

- App 独占临时程序、配置、数据库、凭据、当前服务进程和 SDK session。没有外部实例或既有数据参数。
- Report 保存模式、请求分区、源码与二进制指纹、步骤、入口覆盖、清理及证据位置。凭据和 session 不可序列化进入报告。
- Step 保存动作、入口和非敏感期望/观察，不保存原始 OAuth 载荷。
- 一个运行只驱动一个当前服务实例，恢复时先停旧进程再起新进程。每个分区前 doctor，意外失败后复查并停下。
- evidence 位于独立持久输出目录；临时运行态清理不能删除证据。

## 实施与验证门禁

1. 先保存产品文件校验基线，明确只写本目录。
2. 分区只读核对源码，确认每个用户入口和证据缺口。
3. 驱动先写缺失方法/索引错误/报告安全等失败单测，再实现最小可用入口。子 agent 只跑技能包单测，实际服务驱动归主 agent。
4. 编写主技能及五个四节式 feature 文件，检查索引与源码注册表。
5. 主 agent 审查脚本，按自身文档执行 check、doctor、全图 run，再核对精确报告、样本、进程回收和源文件不变。
6. 若是 harness 漂移，只修改本目录并重新驱动；若为产品缺陷，记录边界并停止扩大范围。

设计不要求为了本轮维护创建 PR、安装全局技能、启动守护服务或更改生产配置。它也不把代码生成完成当作 live pass。
